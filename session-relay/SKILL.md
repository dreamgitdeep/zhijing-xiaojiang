# 会话接力（Session Relay）

把当前会话整理成一份写给**下一个 agent** 的交接笔记（baton），而不是一份写给用户的回顾总结。协议源自开源项目 [relayhand](https://github.com/yanlin-cheng/relayhand)（MIT）。

## 写作心法

**通篇克制，只有「下一步」详细。** 模板按状态组织，不按时间组织——没有「我们先讨论了……然后……」的位置。

## 工作流

1. **确认下一棒任务**：若用户给定了下一棒任务，任务就是过滤器——只总结该任务需要的背景、决策、文件、坑位；无关内容再重要也不写，标题围绕该任务拟。未给定则做通用交接。
2. **取证**：运行 `git status` 与 `git log --oneline -3` 核对仓库真实状态；用 `date +%Y%m%d-%H%M` 获取时间戳 `<TS>`。笔记里的状态、提交号、文件清单必须与仓库实际一致。
3. **按模板写交接笔记**（见下），语言跟随会话（中文会话写中文笔记）。
4. **输出**：
   - 在回复中完整展示交接笔记供用户审阅（用户可能要求重写）；
   - 回复末尾输出一个可整段复制的代码块（格式见「接力提示词」）；
   - 代码块下方（不在块内）加一行人类可读提示：粘贴后把新对话重命名为 `relayhand-<TS>`，并建议将笔记另存为 `relayhand-<TS>.md`，保持接力链可追溯。

## 交接笔记模板

没有内容可写的章节直接删掉，绝不凑数。

```markdown
# 交接：<一句话点名任务与状态>

## 目标
<一句话：在做什么/修什么，为什么。超过一句说明没提炼到位，重写>

## 状态
- 已完成：<清单，一行一项，含关键 commit 号>
- 进行中：<当前正在做的事>
- 阻塞：<障碍、未决问题>

## 关键决策（影响后续）
<只写影响后续工作的技术选择，以及为什么>

## 坑位（勿重蹈）
<失败的尝试及原因；调试结论写成 症状 → 根因 → 修复>

## 下一步
<按序、可照做的行动，足够具体到直接执行。★ 唯一允许详细的章节>

## 文件
读：<从会话中提取的真实路径>
改：<从会话中提取的真实路径；未提交的工作区改动也算，严禁在改动未落定时声称文件未动>

## 来源真相
<完整转录/持久真相源的位置；缺细节时回哪里查。若本会话本身由接力而来，写上一棒的标识，保持接力链可溯>
```

## 写作纪律

1. 读者是下一个 agent，不是用户：写「接力棒」，不写「回顾」。
2. 不叙述对话过程，只写结论性状态。
3. 只写事实，不写感觉；每个字都要帮下一棒干活。
4. 「下一步」是唯一允许详细的章节，其余章节都为它服务。
5. 用户给了下一棒任务时，任务即过滤器。
6. **用户最新指令若改变了下一步做什么，必须在「下一步」中逐字引用**，不得转述成总结者的理解。
7. 本会话若由交接笔记开始，把上一棒标识写进「来源真相」，保持接力链可溯。
8. 文件清单必须从会话中真实发生的读写提取，不得凭记忆编造。
9. **脱敏**：API key、密码、邀请码、个人信息不得写入笔记。
10. 既有产物（计划文档、commit、issue）只引用路径或链接，不复制内容。

## 接力提示词（代码块固定格式）

第一行是命名种子：多数 AI 产品会用首条消息给会话自动命名，这一行把新会话的标题引到接力链上。

```
Relay relayhand-<TS> — <一句话任务，跟随会话语言>

你正在接手一个接力任务。下面是上一会话的交接笔记。请完整阅读，不要复述其内容，然后直接开始执行「下一步」部分。先运行 `git status` 将仓库实际状态与笔记对账；若不一致，先对账再动手。

<交接笔记全文>
```

## 边界

- 笔记中的仓库状态（提交号、工作树干净与否、服务存活）必须实测，不得沿用会话中过时的印象。
- 若工作树有未提交改动，在「状态」与「文件」中如实写明，并提示下一棒先处理。
- 交接笔记本身默认只展示在回复里；是否落盘为 `relayhand-<TS>.md` 由用户决定，不主动写入项目仓库。
